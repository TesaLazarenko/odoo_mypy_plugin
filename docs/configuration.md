## The overlay root

Odoo 18 makes an addon importable only as `odoo.addons.<name>`, and addons import each
other (and their own `tests.common`) that way:
`from odoo.addons.my_base.models.x import Y`. mypy can resolve these imports only from a
`mypy_path` root in which `odoo/addons` holds your addons next to Odoo's.

`odoo-typing-root` (installed with the plugin) generates that root, made of symlinks,
from the `[tool.odoo_typing]` settings:

- `odoo/<entry>` symlinks to every entry of the Odoo package except `addons/`;
- `odoo/addons/<name>` symlinks to every core addon and every `addons_path` addon (a
  core addon wins a name clash, as in Odoo).

`--config FILE` and `--output DIR` override the defaults (`pyproject.toml`,
`overlay_root`). Existing files in the root are left alone, except an earlier generated
`odoo/` or a plain `odoo` symlink.

After adding or removing an addon, run `odoo-typing-root` again: the plugin warns once
per run when the overlay root no longer links the addons on the addons paths.

## Full example

```toml
# pyproject.toml of the project that contains your addons
[tool.mypy]
plugins = ["odoo_typing.plugin"]
mypy_path = [".odoo-root"]           # the generated root, and nothing else of Odoo's
check_untyped_defs = true            # Odoo methods are rarely annotated

[[tool.mypy.overrides]]
module = ["odoo", "odoo.*"]
follow_imports = "silent"            # don't report errors inside Odoo (or unchecked addons)

[tool.odoo_typing]
odoo_version = 18
odoo_path = "/usr/lib/python3/dist-packages/odoo"
addons_path = ["addons"]
overlay_root = ".odoo-root"
dynamic_env = "any"
vals_ignore_keys = ["x_*"]
literal_selection = false
required_values = true
rebound_variables = true
new_record_ids = false
scan_cache_dir = "~/.cache/odoo-typing/scans"
```

## Options

Unknown keys in `[tool.odoo_typing]` are a configuration error, so a typo such as
`addon_path` does not go unnoticed. Relative paths are relative to the file that
contains them.

| Option | Default | Meaning |
|---|---|---|
| `odoo_version` | — (required) | The Odoo major version the checks target: 17, 18, 19 or 20 |
| `odoo_path` | auto-detected | The `odoo` package directory (the one with `release.py`) |
| `addons_path` | `[]` | Directories that *contain* addons, like Odoo's `--addons-path` |
| `overlay_root` | none | The root generated by `odoo-typing-root` |
| `dynamic_env` | `"any"` | Type of `env[name]` when `name` is not a literal: `"any"` or `"base"` |
| `vals_ignore_keys` | `["x_*"]` | Glob patterns of `vals` keys never reported as unknown fields |
| `literal_selection` | `false` | Read `Selection` fields as `Literal[<keys>] \| Literal[False]` |
| `required_values` | `true` | Read required fields and `display_name` without `\| Literal[False]` |
| `rebound_variables` | `true` | A local variable bound more than once has the type of each value at its binding |
| `new_record_ids` | `false` | Read `record.id` as `int \| NewId` (Odoo 17, 18), not as `int` |
| `scan_cache_dir` | `~/.cache/odoo-typing/scans` | Addon scans shared by every project, a subdirectory per interpreter; `""` keeps them in mypy's cache |

**`odoo_version`** is the single source of truth for the version: the plugin picks the
names of Odoo's classes for its hooks from it (Odoo 19 moved the ORM to `odoo.orm`).
Without `odoo_version`, or with a version that is not supported yet, mypy stops with a
message (exit status 2). The Odoo found at `odoo_path` is only compared with it (its
`release.py`), and a warning on stderr names what does not fit; mypy goes on:

- another final release: `odoo_version = 18, but the Odoo at ... is Odoo 19.0; the
  checks follow odoo_version, so set it to 19 or point odoo_path at an Odoo 18`;
- an intermediate (SaaS or development) version, such as `saas~18.3`, also of the
  configured major: odoo-typing supports only the final releases 17.0 to 20.0, so some
  checks may be missing or wrong;
- a major the plugin does not support: `... is Odoo 16.0, which odoo-typing does not
  support (only 17.0 to 20.0); point odoo_path at an Odoo 18`;
- an Odoo that does not define the classes the profile of `odoo_version` expects
  (`BaseModel`, `Environment`, `Many2one`... in the modules where that version defines
  them), as when `odoo_version` or `odoo_path` is wrong or the tree is an intermediate
  version. The hooks are keyed on those names, so the checks would be silently
  incomplete:

```text
odoo-typing: warning: the Odoo at /src/odoo/odoo is Odoo 18.3, an intermediate (SaaS or development) version, and odoo_version = 18: odoo-typing supports the final releases 17.0 to 20.0, so some checks may be missing or wrong
odoo-typing: warning: the Odoo at /src/odoo/odoo does not define odoo.orm.models.BaseModel, odoo.orm.identifiers.NewId, odoo.orm.environments.Environment, ..., which the Odoo 19 profile expects: odoo_version or odoo_path is wrong, or this is an intermediate (SaaS or development) version; checks would be silently incomplete
```

**`odoo_path`**: without it, the plugin looks for an `odoo` package (a directory with
`release.py`) on `mypy_path`, then tries to import `odoo` in mypy's own interpreter,
which usually fails in a virtualenv.

**`addons_path`**: each entry must be a directory that *contains* addons (subdirectories
with a `__manifest__.py`). Listing an addon directory itself, or a directory without any
addon, is a configuration error. A subdirectory that cannot be read (`lost+found` at the
root of a volume) is not an addon, as for Odoo; nor are `__pycache__` and the
directories whose name starts with `.` (`.git`, `.idea`, `.mypy_cache`). Those are not
stamped either, so git or IDE activity in a repository that is itself an addons path
does not make the plugin read the manifests again. A symlink loop in a root skips only
that entry.

**`dynamic_env = "base"`** keeps plain mypy's `BaseModel` for `env[name]` when `name` is
not a literal (or a `Final` / `Literal` str): every field read on it is then an
`attr-defined` error. The default `"any"` leaves such code unchecked. The same goes for
`env.ref(...)` of an id whose model is not known (made at run time, or given by
`_update_xmlids`), which Odoo 19 and 20 declare as `BaseModel`.

**`vals_ignore_keys`** lists glob patterns (case-sensitive) of `vals` keys that are not
reported as unknown fields. The default `["x_*"]` covers fields created in the database
(manual and Studio fields). Their values are still checked when the code declares them.
The same names are not reported where other checks name fields either: domains,
`mapped` / `filtered` / `sorted` / `grouped`, `read` / `fetch`, `_read_group`, orders,
`@api.depends`. There a near miss of a declared field (`x_scroe` for `x_score`) is
still reported as a typo.

**`required_values`** (on by default) reads a field that is required (`required=True`,
as the merged definitions of the model leave it, also a field delegated through
`_inherits` from a required one, and a `related=` path of required `Many2one` fields to a
required field, such as `product.template.attribute.value.name`), a text field whose
compute methods always assign a string (below), `display_name`, `create_date`, `write_date` and
`parent_path` of a model with `_parent_store` as
their value type without `| Literal[False]`: `", ".join(records.mapped("name"))`, `Telegram(bot.token)`,
`format_date(env, rec.date)` and `rows[0]["partner_id"][0]` of a `read()` then type-check. On the 37 core addons of the
benchmark's `big` profile about half of the `... | Literal[False]` errors are of required
fields or `display_name`. A value that types a variable whose later values are checked
against it keeps the declared type: mypy takes a variable's type from its first value,
so `date = move.date` (required) would make `date = line.date` (not required) in the
other arm of an `if` an error; the same holds for the items of a list or dict that is
filled in several statements, and for the first item appended to an empty list that
later gets `False` as written (`rows.append((tag.display_name, ...))`, then
`rows.append((False, ...))`); a value of a field that may be empty appended after the
first one is reported where it is appended. A variable that `rebound_variables` declares
`Any` takes each value as it is, and so does one that only `+=` changes
(`label = self.name`, then `label += " (x)"`): there the required value reads without
`False`. Odoo does read `False` for a required field of a new record
(`new()`, a form's onchange) before the value is set: `required_values = false` reads
these fields as Odoo declares them, for code that must handle such records.

**`new_record_ids`** (off by default) is the same choice for `record.id`. Odoo 18
declares it `int | NewId | Literal[False]` (the plugin declares the same for Odoo 17,
which has no annotation): the id of a record of `new()` or of a form's onchange is a
`NewId`. Every `values[record.id]` of a `dict[int, ...]`, `int(record.id)` and call of a
function that takes `id: int` is then an `arg-type` error, though the records of
`search`, `browse` and `create` have an `int`. By default `record.id` reads as `int`;
`new_record_ids = true` reads it as Odoo declares it, for code that must handle new
records (use `record._origin.id`, `record.ids`, or test `isinstance(record.id, int)`).
`record.id.origin` reads as the `NewId` either way: only a new record has it.
Odoo 19 and 20 leave `record.id` untyped (`Any`), with or without the option.

A computed text field counts as set when Odoo cannot read `False` from it. That is a
`Char`, `Text` or `Html` field with a `compute` method that is not stored, has no
`inverse` and is not `readonly=False`: each read computes it, and for a record the
compute method gave no value Odoo raises "Compute method failed to assign" instead of
reading `False`. Such a field reads as `str` when a class of the model defines the
compute method and assigns the field in it, and every value that the methods of the
model's classes assign to the field's name is a string: a literal, an f-string,
`"%s" % x`, `"a" + x`, `"{}".format(x)`, `", ".join(x)`, or the call of a name of the
module that is declared to return `str` (`json.dumps(...)`, `str(...)`, a function of
the addon annotated `-> str`). In a `Char` or `Text` field `x or "#"` is a string too,
whatever `x` is: the field turns every value but `None` and `False` into its string
(an `Html` field of Odoo 17-19 keeps it as it is). `record.data = json.dumps(values)` in
two branches of an `if` / `elif` is enough; `record.data = values and json.dumps(values)`,
`record.data = False` in any method of the model (also `record["data"] = False` and
`record.update({"data": False})`), or `record.update({**values})` in the compute method
leave the field `str | Literal[False]`. A value that is not known, written to records
the method's records reach through fields, counts only where the fields may lead back to
the model: `menu.page_id.write({"url": menu.url})` writes pages, `menu.parent_id.write(...)`
menus. The classes are those the reading addon sees: an override of the compute method
in an addon outside its dependencies does not count.

A computed text field with an `inverse` or `readonly=False` (and not stored) reads as
`str` under the same conditions, and only when the compute method assigns it to each
record on every path: Odoo fills in `False` for a record such a method left without a
value. `for menu in self:` whose body assigns `menu.url` in both arms of an `if`, or
before a `continue`, does; so does `self.url = "#"`. A loop over some of the records
(`self.filtered(...)`), an `if` without `else`, a `continue`, `break` or `return` before
the assignment, an assignment inside a `with` or an inner loop, or in a `try` body but
not in each of its `except` handlers do not. The method that counts is the last override
the reading addon sees; one that calls `super().<method>()` on every path hands on to
the method it overrides.

Inside its own compute method the field reads `False` until it is assigned, and inside
its inverse method it holds the value written, so reads there keep the declared type; a
value given from outside the model's classes (`create({"data": False})`, a form that
clears an editable field) is not seen, as with a required field.

**`rebound_variables`** (on by default) gives a local variable without an annotation
that its function binds more than once (`products = []` then records,
`proposal = company` then `proposal = False`, `total = 0` then `total += line.amount`,
one loop variable over two models) the type of each value where it is bound; where
branches that gave it values of different types meet it is `Any`. A variable that a
binding may give `False` keeps it as `Literal[False]`, so `if partner:` leaves the
records. mypy itself takes a variable's type from its first value and reports every
later value of another type. `rebound_variables = false` keeps mypy's inference; mypy's
own `allow_redefinition = true` (with `local_partial_types = true`) widens such a
variable to a union instead, which reports `Literal[True]` items where a variable is
records or `False`. See [rebound variables](checks.md#plain-mypy-errors-you-will-see-more-often).

**`literal_selection = true`** reads a `Selection` field whose keys are literal
(including the `selection_add` of the addon's view) as
`Literal["draft"] | ... | Literal[False]` rather than `str | Literal[False]`, so
comparing it with a key that does not exist is an error. It is off by default because
assigning the value to a variable then fixes the variable's type to those literals.

**`scan_cache_dir`**: see [Shared scan cache](how-it-works.md#shared-scan-cache). The
default is `$XDG_CACHE_HOME/odoo-typing/scans` (`~/.cache/odoo-typing/scans`). The scans
sit in a subdirectory per interpreter, `<scan_cache_dir>/<cache_tag>/` (`cpython-312`),
and the plugin's other records in mypy's cache, in `<cache_dir>/odoo_typing/<cache_tag>/`.
Files directly in `scan_cache_dir` or in `<cache_dir>/odoo_typing/` were written by
earlier versions and can be deleted.

## Odoo 19 and 20

**Odoo 19+**: `odoo` and `odoo.addons` have no `__init__.py` (namespace packages), so
mypy names a file inside them `odoo.addons.<name>...` only with
`explicit_package_bases = true` in `[tool.mypy]`. Set it with `overlay_root` (the plugin
warns if it is missing), and whenever you give mypy files under the Odoo tree.

Odoo 19 declares relational fields `Field[BaseModel]`; the plugin makes `Many2one`,
`One2many` and `Many2many` generic in the comodel (`fields.Many2one[ResPartner]`), as
Odoo 18 declares them.

**Odoo 20** has the names of Odoo 19 plus PEP 695 type parameters (`class Field[T]`), so
mypy must target Python 3.12 or newer (`python_version = "3.12"`, or run mypy on 3.12+);
with an older target the plugin stops with a message. Some addons ship migration scripts
(`migrations/<version>/pre-migrate.py`) that mypy sees as duplicate modules: add
`exclude = "/migrations/"` to `[tool.mypy]`.

## Running mypy

```bash
odoo-typing-root                     # (re)generate .odoo-root; again after adding/removing addons
mypy -p odoo.addons.my_addon         # or: mypy .odoo-root/odoo/addons/my_addon
odoo-typing-root --check             # in CI: exit 1 if .odoo-root no longer matches the addons
```

`odoo-typing-check` wraps these steps for daily use:

```bash
odoo-typing-check                                 # every addon of addons_path
odoo-typing-check my_addon addons/other_addon     # addons by name or directory
odoo-typing-check addons/my_addon/models/sale.py  # the errors of these files only
odoo-typing-check --daemon my_addon -- --strict   # dmypy; mypy's own options after --
```

It regenerates the overlay root when an addon was added, removed or moved, runs mypy on
the addons the targets belong to (`-p odoo.addons.<name>`), and prints each path as the
real file, relative to the current directory: mypy itself prints
`.odoo-root/odoo/addons/my_addon/models/sale.py`, which is not the file an editor has
open or a CI annotation can attach to. For a file or a directory inside an addon the
whole addon is checked (mypy needs it) and only the errors of those files are printed;
the exit status is then 1 if they have any. `--config FILE` names another config file
than `pyproject.toml`.

Check addons through their `odoo.addons.<name>` name (`-p`, or their path under the
root), **not** through their real directory. mypy names `mypy addons/my_addon` as
`my_addon.*`, and the same files are then analyzed a second time as
`odoo.addons.my_addon.*` wherever they are imported. The plugin warns about this on
stderr (`odoo-typing: warning: mypy names module "my_addon" ...`) and adds no
dependencies for such files.

The plugin is tested with mypy 2.1 to 2.4, and the package requires `mypy>=2.1,<2.5`.
It relies on mypy internals beyond the plugin API, which another mypy version may
change. A mypy outside that range (installed with `--no-deps`, or pinned apart from the
plugin) gets a warning, and mypy goes on. It is printed by each process that loads the
plugin (each `--num-workers` worker; with `dmypy`, in the daemon's log):

```text
odoo-typing: warning: mypy 2.5.0 is not a version odoo-typing is tested with (>=2.1,<2.5); the plugin relies on mypy internals, so expect missed or wrong errors or an INTERNAL ERROR: install a tested mypy
```

## `mypy.ini` and `setup.cfg`

With `mypy.ini`, `.mypy.ini` or `setup.cfg`, use an `[odoo_typing]` section; separate
`addons_path` entries with commas or newlines:

```ini
[mypy]
plugins = odoo_typing.plugin
mypy_path = .odoo-root
check_untyped_defs = true

[mypy-odoo.*]
follow_imports = silent

[odoo_typing]
odoo_version = 18
odoo_path = /usr/lib/python3/dist-packages/odoo
addons_path = addons, ../enterprise
overlay_root = .odoo-root
```

An INI config without that section uses the `[tool.odoo_typing]` table of a
`pyproject.toml` next to it, if there is one.

## Simple setup without the overlay root

Without `overlay_root`, your addons are top-level packages (`my_addon.models.x`), and
`from odoo.addons.my_addon...` imports of them are `import-not-found` and give `Any`.
Use this only if your addons never import each other that way.

```toml
[tool.mypy]
plugins = ["odoo_typing.plugin"]
# 1) a directory that contains the `odoo` package (see the note below)
# 2) your addons directories, so `my_addon.models.x` can be imported
mypy_path = [".odoo-root", "addons"]
check_untyped_defs = true

[[tool.mypy.overrides]]
module = ["odoo", "odoo.*"]
follow_imports = "silent"

[tool.odoo_typing]
odoo_version = 18
odoo_path = ".odoo-root/odoo"        # dir with release.py; auto-detected if omitted
addons_path = ["addons"]
```

> [!NOTE]
> If Odoo is installed as a deb/pip package, don't put the whole
> `site-packages` / `dist-packages` directory on `mypy_path`. Create a directory that
> holds only a symlink instead:
> `mkdir .odoo-root && ln -s /usr/lib/python3/dist-packages/odoo .odoo-root/odoo`.
> For a git checkout, use the checkout root. Then run `mypy addons/my_addon`.

## Configuration errors

A configuration error (Odoo not found, a missing directory, a malformed table) stops
mypy with exit status 2 and one line on stderr, for example:

```text
odoo-typing: error: addons_path entries are not directories: /src/missing
```

A symlink loop in `odoo_path`, `overlay_root` or an `addons_path` entry is a
configuration error too, and so is a `pyproject.toml` that is not UTF-8 when the plugin
reads its `[tool.odoo_typing]` table for a `mypy.ini` without an `[odoo_typing]`
section:

```text
odoo-typing: error: odoo_path /src/odoo cannot be resolved: Symlink loop from '/src/odoo'
odoo-typing: error: addons_path entry /src/addons cannot be resolved: Symlink loop from '/src/addons'
odoo-typing: error: cannot read /src/pyproject.toml: 'utf-8' codec can't decode byte 0xe9 in position 39: invalid continuation byte
```

The first two are given by Python 3.11 and 3.12. Python 3.13 does not raise on a loop,
so the path then gives the error of a missing directory
(`odoo_path ... does not contain release.py`, `addons_path entries are not directories`).
